# Insurance Fraud Detection — Data Dictionary

## 1. Overview

This dictionary documents the fields generated by `src/generator.py`. The generator returns eight operational datasets and one separate ground-truth dataset.

Unless otherwise stated, generated identifiers are strings, dates use ISO format (`YYYY-MM-DD`), and monetary values are decimal numbers rounded to two decimal places.

Synthetic names, email addresses, locations, and tax identifiers are generated for testing. They do not represent verified real-world records.

## 2. Claimant

**Primary key:** `claimant_id`

| Field | Type | Required | Description and validation |
|---|---|---|---|
| `claimant_id` | String | Yes | Unique synthetic claimant ID, such as `CLT-000001`. |
| `full_name` | String | Yes | Synthetic claimant name. |
| `email` | String | Yes | Synthetic email using the `example.test` domain. |
| `phone` | String | Yes | Synthetic contact number. Ten planted-pattern claimants share `900SUSPICIOUS`. |
| `address_id` | String | Yes | Synthetic address-group ID. Repeated values represent shared addresses. |

## 3. Provider

**Primary key:** `provider_id`

| Field | Type | Required | Description and validation |
|---|---|---|---|
| `provider_id` | String | Yes | Unique provider ID, such as `PRV-000001`. |
| `provider_name` | String | Yes | Synthetic provider name. |
| `provider_type` | String | Yes | One of `HOSPITAL`, `CLINIC`, `REPAIR_SHOP`, `PHARMACY`. |
| `tax_id` | String | Yes | Synthetic tax identifier, such as `SYNTH-TAX-000001`. |
| `address_id` | String | Yes | Synthetic address-group ID. |

The generator creates distinct provider IDs and tax-ID values. Additional database or validation enforcement of tax-ID uniqueness should be confirmed separately.

## 4. Policy

**Primary key:** `policy_id`

| Field | Type | Required | Description and validation |
|---|---|---|---|
| `policy_id` | String | Yes | Unique policy ID, such as `POL-000001`. |
| `claimant_id` | String | Yes | References the claimant associated with the policy. |
| `policy_type` | String | Yes | One of `HEALTH`, `AUTO`, `PROPERTY`. |
| `start_date` | Date string | Yes | Policy coverage start date. |
| `end_date` | Date string | Yes | Policy coverage end date; later than the start date in generated records. |
| `coverage_limit` | Decimal | Yes | Positive monetary coverage limit. |
| `status` | String | Yes | Generated as `ACTIVE`. |

The default generator creates one policy per claimant.

## 5. Incident

**Primary key:** `incident_id`

| Field | Type | Required | Description and validation |
|---|---|---|---|
| `incident_id` | String | Yes | Incident ID containing the year and sequence number, such as `INC-2025-000001`. |
| `incident_date` | Date string | Yes | Synthetic incident date. |
| `incident_type` | String | Yes | One of `ILLNESS`, `ACCIDENT`, `PROPERTY_DAMAGE`, `THEFT`. |
| `location` | String | Yes | Synthetic location label. |
| `description` | String | Yes | Synthetic incident description. |

Generated incident dates use years 2024, 2025, or 2026.

## 6. Claim

**Primary key:** `claim_id`

| Field | Type | Required | Description and validation |
|---|---|---|---|
| `claim_id` | String | Yes | Claim ID, such as `CLM-2026-000001`. |
| `claimant_id` | String | Yes | References the claimant submitting the claim. |
| `policy_id` | String | Yes | References the policy associated with the claim. |
| `incident_id` | String | Yes | References the associated incident. |
| `provider_id` | String | Yes | References the provider associated with the claim. |
| `claim_date` | Date string | Yes | Currently set to the incident date by the generator. |
| `claimed_amount` | Decimal | Yes | Generated monetary amount, from 500.00 to 25,000.00. |
| `approved_amount` | Decimal | Yes | Generated positive amount no greater than the claimed amount or policy coverage limit. |
| `status` | String | Yes | One of `SUBMITTED`, `UNDER_REVIEW`, `APPROVED`, `REJECTED`, `PAID`. |

The generator deliberately assigns a shared provider to claims belonging to ten selected claimants. Ground-truth labels are assigned separately.

## 7. Invoice

**Primary key:** `invoice_id`

| Field | Type | Required | Description and validation |
|---|---|---|---|
| `invoice_id` | String | Yes | Provider-based invoice ID, such as `INV-PRV-000001-000001`. |
| `claim_id` | String | Yes | References the associated claim. One invoice is generated per claim. |
| `provider_id` | String | Yes | References the provider associated with the claim. |
| `invoice_amount` | Decimal | Yes | Equals the claim's `claimed_amount` in generated records. |
| `invoice_date` | Date string | Yes | Equals the claim's `claim_date` in generated records. |
| `status` | String | Yes | `REJECTED` when the claim is rejected; otherwise `SUBMITTED`. |

The current database schema enforces one invoice per claim.

## 8. Payment

**Primary key:** `payment_id`

| Field | Type | Required | Description and validation |
|---|---|---|---|
| `payment_id` | String | Yes | Payment ID, such as `PAY-2026-000001`. |
| `claim_id` | String | Yes | References the associated claim. |
| `invoice_id` | String | Yes | References the invoice associated with the payment. |
| `payment_amount` | Decimal | Yes | Positive amount generated as a portion of the claim's approved amount. |
| `payment_date` | Date string | Yes | Equals the claim's `claim_date` in generated records. |
| `status` | String | Yes | `PENDING` for an `APPROVED` claim or `COMPLETED` for a `PAID` claim. |

Payments are generated only for claims with status `APPROVED` or `PAID`. The generated payment amount can be lower than the full approved amount.

## 9. RelationshipEdge

**Primary key:** `edge_id`

| Field | Type | Required | Description and validation |
|---|---|---|---|
| `edge_id` | String | Yes | Unique edge ID, such as `EDGE-000001`. |
| `source_id` | String | Yes | ID of the source entity. |
| `target_id` | String | Yes | ID of the target entity. |
| `edge_type` | String | Yes | Relationship category identifying the connection. |
| `effective_date` | Date string | Yes | Generated as `2026-01-01`. |
| `is_planted_suspicious` | Boolean | Yes | True for planted shared-contact edges; false otherwise. This field is reserved for synthetic ground-truth analysis, not risk-scoring input. |

Relationship types generated by the current code include:

- `CLAIM_USES_PROVIDER`
- `CLAIMANT_HAS_POLICY`
- `SHARES_CONTACT`
- `SHARES_ADDRESS`
- `CLAIM_LINKED_TO_INCIDENT`

Source and target IDs are stored as generic strings. The validator checks the endpoint IDs and applies relationship-type rules; this table does not use dedicated foreign-key columns for each entity type.

## 10. Ground Truth

**Purpose:** Separate synthetic evaluation labels. This dataset must not be used as a fraud-detection input.

| Field | Type | Required | Description and validation |
|---|---|---|---|
| `record_type` | String | Yes | `CLAIM` or `RELATIONSHIP_EDGE`. |
| `record_id` | String | Yes | ID of the claim or relationship edge being labelled. |
| `is_planted_suspicious` | Boolean | Yes | Indicates whether the record is part of a deliberately planted synthetic pattern. |
| `reason` | String | Yes | `PLANTED_SHARED_CONTACT_PROVIDER_PATTERN`, `PLANTED_SHARED_CONTACT_PATTERN`, or `SYNTHETIC_BASELINE`, depending on the record. |

Claim labels identify claims belonging to the selected claimant group. Relationship-edge labels identify the planted shared-contact edges. These labels describe the generator's design, not confirmed real-world fraud.

## 11. Important Validation and Interpretation Notes

- Primary identifiers should be unique within their respective datasets.
- Claim references should resolve to existing claimant, policy, incident, and provider records.
- Invoice and payment references should resolve to the correct claim and invoice.
- Generated claim amounts, approved amounts, invoice amounts, and payment amounts should satisfy the rules enforced by the validation code and database schema.
- Shared addresses can occur among benign claimants. A shared address alone is not proof of fraud.
- Shared contact information and common providers are risk indicators that require investigation, not proof of wrongdoing.
- Ground truth is kept separate from the operational datasets and is used only for evaluation.
- Evaluation results from deliberately planted patterns should not be interpreted as real-world fraud-detection accuracy.
